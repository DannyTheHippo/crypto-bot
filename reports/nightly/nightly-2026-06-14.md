## 2. Root cause (Step B) — verified in source, not a symptom

The weighted-average entry-price division in `src/domain/oms/position.ts` (increasing / add-to-position branch):

```
avgEntry = absOld·avgEntry + fillQty·fillPrice) / (absOld + fillQty)
```

Under the global `Decimal` config (`precision: 40`, `setupDecimal()` in `money.ts`) the quotient is non-terminating (34–35 dp). It was then minted as `price(result.position.avgEntry)` at `src/modules/execution/portfolio-state.service.ts:69`, where `checkPrecision` (money max = 18 dp) **threw**.

- Fires **only on the increasing branch** — which is why the paper soak (flat↔full-exit cycles, never adding) never caught it.
- `avgEntry` is the **unique `checkPrecision`-guarded mint of a computed value in the fill path**. Confirmed by grepping every `realizedPnl`/`avgEntry`/money-constructor use-site: `realizedPnl` is held raw on `PositionState`, persisted via `toFixed()` into `NUMERIC(38,18)` (Postgres rounds, no throw), and exported to metrics via `toNumber()` — it is never minted; `notional`/`cashDelta`/`signedQty` are products of venue values or stored raw. Equity (`equity-sampler.service.ts`) computes raw Decimals and is never minted. So the fix does **not** move the stall one fill later.

**Poison-message mechanism:** `DemoFillPollerService.poll()` never advances `this.since` (anchored once at boot), so each cycle re-fetched all post-boot trades and re-threw on the same overflowing fill — aborting the loop and blocking every later fill.

**Damage (operational, from the DB — single-night PnL is NOT judged):** equity 5000 → 4741 → frozen at **4421.54** for ~80 min; `fills` frozen; `open_orders`/`in_flight_intents` climbing unbounded (**14/14** at capture — a failed fill never retires its order). PnL is unmeasurable while ingestion is broken.

## 5. The fix — minimal, pure-domain, money-exact

`avgEntry` is an **internal cost-basis average**, inherently _between_ venue ticks, so it must conform to the money type's own 18-dp maximum (rounding to a venue tick would distort the average). A >18-dp value cannot legally be a `Price`; rounding to 18 dp conforms to the money contract, it does not weaken exactness (same lesson as the prior `roundToStep` sizer fix).

- **`src/domain/types/money.ts`** — new reusable helper beside `roundToTick`/`roundToStep`:
  ```ts
  export function roundToMoneyPrecision(d: Decimal): Decimal {
    return d.toDecimalPlaces(MAX_DECIMAL_PLACES, Decimal.ROUND_HALF_EVEN); // 18 dp, matches the global config
  }
  ```
- **`src/domain/oms/position.ts`** — wrap the increasing-branch division in `roundToMoneyPrecision(...)` (import from `../types/money`; domain→domain, allowed by the boundaries wall).

`ROUND_HALF_EVEN` (the configured default) is unbiased for an internal average; the sub-1e-18 residual in downstream realized PnL is below any venue tick — economically zero. Diff: **5 files, +171/-14** (source: `position.ts` +13, `money.ts` +11; the rest is tests).
