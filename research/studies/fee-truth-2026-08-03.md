# Fee flag / fee ledger truth audit (2026-08-03)

Resolves the standing question: is `fills.fee_resolved` and the `fee_ledger` table (a) vestigial —
scaffolding for a fee-conversion feature never built, or (b) unwired — a real intended behaviour
silently doing nothing. **Verdict: (a), vestigial, on all three surfaces examined.** No promotion
verdict, gate, or measurement reads any of them today; none ever has.

## Scope

Three surfaces, examined independently:

1. `fills.fee_resolved` (DB column).
2. `fee_ledger` (DB table).
3. `FeeLedgerService` (in-memory accumulator, `src/features/trading/execution/fee-ledger.service.ts`)
   — not named in the original finding, but close enough in name and intent to `fee_ledger` that it
   had to be checked separately so a reader does not conflate "the ledger is wired" (true, in one
   sense) with "the ledger is read by anything" (false, in every sense).

## 1. `fills.fee_resolved`

**History.** Present since the repo's first commit (`214eb7d`), carried unchanged through the v3
greenfield schema rewrite (`64e588a`, 2026-07-20). No commit message, spec, or design doc anywhere
in `git log --all -S feeResolved` explains what "resolved" was meant to mean or what would set it
true. There is no evidence a resolution feature was ever designed, only that the column was
scaffolded.

**Every writer.** Exactly one INSERT path exists for `fills`:
`src/database/repositories/trading/drizzle-execution-store.ts:220-237` (`saveFill`), which passes
`feeResolved: false` unconditionally (`:230`). `FillRepository.insertIdempotent` is the table's only
other write entry point and has no UPDATE method at all — there is no code path, anywhere in `src/`,
that could ever set the column to `true`. Confirmed by exhaustive search: `grep -rn
"insertIdempotent|saveFill" src/` returns one call site.

**Every reader.** None. `PromotionStatsRepository.fillsForMode`
(`src/database/repositories/trading/promotion-stats.repository.ts:54-66`) is the sole query that
turns `fills` rows into promotion-gate evidence, and its `select({...})` does not project
`feeResolved` — the column never leaves Postgres. Downstream, `walkRoundTrips` and `sumFeesQuote`
(`src/domain/trading/risk/round-trips.ts`) decide `UNCONVERTIBLE_FEE_ASSET` purely from
`fill.feeAsset` compared against the traded symbol's own base/quote asset
(`isBaseAsset`/`quoteAssetOf`, `round-trips.ts:99-114, 167-175, 224-231`) — never from a resolved
flag. `PromotionReadinessService.evaluate` (`src/features/trading/mode-control/
promotion-readiness.service.ts:84-129`) consumes only that result. The flag is written, never read,
by anything in the production path or the research path.

**Conclusion:** decorative. The promotion gate's fee-convertibility check is — and always was —
computed directly from `fee_ccy` vs. the symbol's base/quote asset, never gated on this flag. The
gate's correctness (established separately: every fee currency observed live is the symbol's own
quote or base, so `unconvertibleFeeAsset` is correctly `false` today) does not depend on
`fee_resolved` in any way.

## 2. `fee_ledger` (DB table)

**History.** Same as above — present since `214eb7d`, unchanged through the v3 rewrite. No commit
introduces a writer.

**Every writer.** None. `grep -rn "schema.feeLedger" src/` returns only the table's own definition
in `trading.schema.ts:183-191`. No repository, service, or migration script ever inserts into it.

**Every reader.** None. Same search, same result — zero references outside the schema file.

**Conclusion:** a fully inert table. Zero rows is not a symptom of anything failing; it is the only
state the table has ever been capable of holding, in a live stack that has been running fills since
before the v3 rewrite.

## 3. `FeeLedgerService` (in-memory accumulator)

This one is genuinely different in kind, and worth separating from the DB table above precisely
because its own header comments assert consumers that do not exist — the exact "reads as healthy
without ever having established anything" pattern the finding warned about.

**What it does.** `applyFillToPortfolio` (`src/domain/trading/oms/portfolio-fill.ts:43-47`) routes a
fill's fee to one of three buckets per §6.6: quote-asset fees hit cash + PnL, base-asset fees shave
retained base, and any THIRD asset (e.g. BNB on a BTC/USDT fill) is returned as `feeLedger: {
asset, amount }` instead. `PortfolioStateService.applyFill`
(`src/features/trading/execution/portfolio-state.service.ts:138`) forwards that into
`FeeLedgerService.add()` — so the accumulator IS wired and IS fed on every third-asset-fee fill.

**What reads it.** Nothing. `FeeLedgerService.total()` and `.all()`
(`fee-ledger.service.ts:15-21`) have zero call sites anywhere in `src/` — confirmed by exhaustive
search. `.add()` is the only method ever invoked. The service's own header comment
(`fee-ledger.service.ts:4-6`) and `portfolio-fill.ts`'s header comment (`:13-14`) both claim the
accumulated total "participates in balance reconciliation" and that "PnL reporting converts at
fill-time mark (flagged estimate) elsewhere." Neither claim is true today:
`ReconciliationService` (`src/features/trading/execution/reconciliation.service.ts`) never imports
or references `FeeLedgerService`, and no PnL-reporting code path converts a third-asset fee total at
mark anywhere in the repo. Those two sentences describe a feature that was designed-for but never
built, stated as though it already exists.

**Conclusion:** the accumulator is write-only. It costs nothing (a `Map<string, Decimal>`, per-boot,
never persisted) and breaks nothing — third-asset fees are correctly excluded from cash/PnL either
way, per §6.6 — but nothing downstream ever consults the number it accumulates. It is not "unwired"
in the sense of a broken pipe; it is a pipe that terminates in a bucket nobody has plumbed a drain
out of yet.

## Why this is not a promotion-gate risk

The live data anti-join (already established) found every observed fee currency is the symbol's own
quote or base — no third-asset fee (BNB or otherwise) has occurred on this book to date. So
`FeeLedgerService` has likely never accumulated a nonzero total in production, and even if it had,
nothing reads it, so it could not have silently corrupted a verdict. `fee_resolved`'s truthiness
was never load-bearing for the same reason: the gate recomputes convertibility itself, every time,
from the raw fee currency.

## What the fee-floor derivation should cite

Already correct. `research/studies/fee-floor-derivation-2026-07-31.md` § 2 already names
`fills.fee_amount` (+ `fee_ccy`, `price`, `qty`, `liquidity`) as the source of truth and reproduces
`sumFeesQuote`'s own conversion rule. It never cited `fee_resolved` or `fee_ledger`. No change
needed there.

## Disposition

**Prefer the smaller honest change, per the dispatch brief.** Dropping `fee_resolved` and
`fee_ledger` is a schema migration; this repo treats migrations as deliberate, reviewed changes
(see `drizzle/0001_v3_append_only_hardening.sql`). This pass does NOT write that migration.

Instead, this pass:

1. Annotates all four touch points (`trading.schema.ts`'s `feeResolved` column and `feeLedger`
   table, `drizzle-execution-store.ts`'s hardcoded `false`, and `fee-ledger.service.ts` /
   `portfolio-fill.ts`'s header comments) so the next reader cannot mistake any of the three
   surfaces for a working, consumed feature.
2. Corrects the two comments that asserted false consumers ("participates in balance
   reconciliation", "PnL reporting converts at mark elsewhere") to state plainly that no such
   consumer exists today.
3. Leaves the DB column, DB table, and in-memory accumulator in place, unmodified in behavior — no
   runtime path changes, so no new spec coverage is required by this pass.

**Follow-up surfaced, not actioned:** a migration dropping `fills.fee_resolved` and the `fee_ledger`
table, OR a decision to actually wire a third-asset-fee reconciliation/mark-to-market reader for
`FeeLedgerService`, is an owner-scoped decision this pass does not make.
